## Problem Statement

The D4Y Dental Pathway Program site works, but it reads as overwhelming. The home page stacks 5 long sections of program copy, and the signed-in areas are dense. The developer (who ships what the D4Y founders specify, and does not own program scope) wants three things before the pilot cohort uses it:

1. A cleaner, simpler UI in the style of two reference screenshots (modern SaaS landing pages), keeping D4Y's green.
2. The code moved to TypeScript and an industry-standard front-end stack (Tailwind was the open question).
3. CLAUDE.md updated to match.

This repo stays strictly front end. The backend will be a small Node/Express API in a separate repo, with Supabase for auth and data. Neither exists yet.

## Demand Evidence

Out of scope for this session by the developer's call: "i am just dev, i am in charge of shipping the app, i am just building what i am told by the founders." Program demand belongs to the D4Y founders, and the pilot cohort is their demand test (the 25-seat capacity in the demo data module is sample data, not a confirmed size). What this design controls is not over-building: the redesign stays on sample data and adds no backend.

## Constraints

- Strictly front end. No Express, no Supabase client, no auth wiring in this branch. `src/data/demo.js` stays the stand-in for the database.
- Content traces to the D4Y proposal or the portal prototype. Budget, revenue math, reviewer pay, sponsorship notes, and the doc's stray margin notes never appear on the site.
- The proposal lists 5 modules; the site keeps 7 (DAT Preparation and Interview Preparation come from the portal prototype).
- No fake UI, ratings, logo walls, user counts or placeholder stats, even though both references use them.
- Accessibility: landmarks, one `h1` per page, visible focus, `prefers-reduced-motion`, no horizontal scroll at 390px and 1360px.

## Premises (agreed)

1. Pilot scope only: public site plus student, mentor and admin areas, all on sample data.
2. Take the references' layout (floating pill nav, large centered headline, generous whitespace, soft rounded cards, faint concentric rings, light theme in D4Y green). Drop their ornament (activity cards, ratings, logo walls, floating app icons, 3D globe).
   - **Decision: the hero rings are the one allowed decorative element.** They are the core of the requested style and carry no false claim, unlike ratings or fake cards. Built in pure CSS, `aria-hidden`, hero only, static (no animation). The new CLAUDE.md records this exception ("faint concentric rings behind the hero as the only decoration"). It's part of the founders' wireframe sign-off (Gate 1); if they decline, the rings are removed and nothing else changes.
3. "Simpler" means fewer sections and less text per page, not less program. Every module, package and the hardship seat stays reachable.
4. Stack: strict TypeScript, Vite + React Router (no Next.js: no server rendering is needed and the API is a separate Express app), Tailwind v4 replacing hand-written CSS, same `app → features → shared → data` folders.
5. Work on `feat/pilot-redesign` in stages that each build on their own.
6. CLAUDE.md rewritten for the new system; README's "FastAPI" corrected to Express.

## Approaches Considered

- **A: Restyle in place** (plain CSS, then rename to TS). Rejected: keeps ~4,000 lines of CSS with ~20 font sizes and no type scale, and skips Tailwind.
- **B: Staged rebuild with own primitives.** Chosen.
- **C: Staged rebuild on shadcn/ui.** Rejected for now: adds Radix packages and a generic default look. Individual shadcn components (dialog, dropdown) can be pulled in later if admin needs them.

### R2-1 — feasibility (blocking)

**Problem**

> The declared order `@layer legacy, theme, base, components, utilities;` puts Tailwind's preflight (emitted in layer `base`) above every legacy rule, not just legacy base.css. Layer order beats specificity, so preflight's `*, ::before, ::after { margin: 0; padding: 0; border: 0 solid }`, heading font-size/weight inherit, link color inherit, button background reset and list-style none override legacy class rules too (e.g. `.button`, `.section-wrap`, `.hero h1`). Un-migrated pages will lose spacing, borders, heading sizes and button styling during Stages 2-4, which contradicts the design's own claim that legacy rules 'still style un-migrated ones' and the round-1 obligation that preflight not reset un-migrated pages. The Stage 2 screenshot check would catch this but the chosen strategy guarantees it fails.

**Remedy**

> Either order legacy between base and components (`@layer theme, base, legacy, components, utilities;`, declared before `@import "tailwindcss"`) so legacy beats preflight but loses to utilities, or turn preflight off until Stage 5 by importing only `tailwindcss/theme.css` and `tailwindcss/utilities.css` with their layers. State which, and keep the before/after screenshot check.
